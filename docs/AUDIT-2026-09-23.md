# Workflow determinism audit — 2026-09-23

## Scope

Reviewed the agent contract, design and workflow documents, quality gates, templates, validator, registers, and September meal-order sessions. The audit focused on repeated user/agent exchanges, ambiguous transitions, resumability, and divergence between transactional records and cooking artifacts.

## What is already working

- The meal-to-order lifecycle has stable phase gates and an explicit final-purchase confirmation boundary.
- Canonical meal selection, ingredient/cart reconciliation, package allocation, and receipt retention have named sources of truth.
- The shopping review has converged on one useful user response: on-hand ingredients plus additional groceries, followed immediately by cart construction.
- Cart revisions consistently require a new exact approval snapshot.
- Cooking feedback is separated from purchase completion, and validated recipes require a positive cooked outcome.

## Repeated interaction pattern

The observed sessions consistently follow this sequence:

1. User states a meal goal.
2. Agent researches and presents candidates.
3. User selects or refines the meal.
4. Agent presents scaled recipe needs and one consolidated shopping question.
5. User identifies pantry items and extras.
6. Agent builds and reconciles the cart.
7. User selects fulfillment and may change the window or add groceries.
8. Agent presents a fresh exact snapshot.
9. User confirms; agent places and verifies the order.
10. Agent produces the cooking artifact.
11. User reports the cooked outcome and later refinements.

## Gaps found

### 1. Next-action ownership was implicit

Run status described the past state but did not always say who should act next. This made short replies and interrupted sessions harder to resume deterministically.

**Change:** Run schema version 3 and session schema version 2 add an explicit `handoff` containing one owner, next action, awaited event, and timestamp. Workflow and quality rules now define the supported checkpoint vocabulary.

### 2. Short responses depended too heavily on chat reconstruction

Replies such as `Pickup`, `Confirm`, or `Print the recipe` are safe only in a known checkpoint.

**Change:** The workflow now maps common short responses to the active handoff. `Confirm` can authorize purchase only at `confirm-exact-cart` for the unchanged snapshot.

### 3. User-facing response shapes were inconsistent

Some stages invited redundant confirmation while others did not clearly end with the one decision needed to proceed.

**Change:** Every checkpoint response now leads with the resulting state, includes only decision evidence, names invalidations, and ends with at most one action matching the handoff. Agent-owned reversible work continues automatically.

### 4. Session boundaries were underspecified

Cooking feedback and corrections often arrive after the order or initial deliverable, while audits and maintenance are separate practical requests.

**Change:** A session now follows a practical request rather than every message or the whole chat window. Direct outcome corrections remain attached to the originating session; separate audits receive their own maintenance session.

### 5. Recipe and printable-card content can drift

The structured saved recipe and `scripts/build_recipe_cards.py` currently duplicate content. This was exposed when cauliflower and onion changed after printing.

**Change:** The existing open issue remains explicit. Current sources are synchronized, old PDFs are superseded for repeats, and consolidation into one structured source is the next engineering step.

## Follow-up implementation

The recipe-card source issue was resolved later on 2026-09-23. All card content formerly embedded in `scripts/build_recipe_cards.py` was migrated to structured YAML. The revised cauliflower card uses a new v2 filename, preserving the original printed PDF as historical evidence.
